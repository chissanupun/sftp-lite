# SFTP-Lite — Prep Notes (อ่านให้เข้าใจ ไม่ใช่ท่อง)

อ่านจนเล่าเป็นคำตัวเองได้โดยไม่มองสคริปต์ — พร้อมอัด

---

## เรื่องราวตั้งแต่ต้น (เล่าแบบนี้)

**จุดเริ่ม — ปัญหาที่เจอเอง**
ทุกครั้งที่ส่งรูป/วิดีโอให้ตัวเองผ่าน LINE เพื่อย้ายจากมือถือไปโน้ตบุ๊ก มันจะโดนบีบอัดคุณภาพเสมอ ทั้งที่สองเครื่องอยู่ห้องเดียวกัน ต่อ WiFi เดียวกัน ไม่ควรต้องพึ่งอินเทอร์เน็ตหรือโดนบีบอัดอะไรเลย — นี่คือจุดเริ่มของไอเดีย: อยากได้ทางส่งไฟล์ตรงระหว่างเครื่อง ไม่ผ่าน cloud ไม่บีบอัด

**คิดโครงสร้างโปรแกรม**
ตัดสินใจว่าต้องมีสองส่วน: ส่วนโอนไฟล์จริง (STORE เก็บ, GET ดึง, LIST ดู, DELETE ลบ) กับส่วนหา server (จะได้ไม่ต้องมานั่งพิมพ์ IP เอง คล้าย AirDrop) — สองงานนี้ลักษณะต่างกันมาก พอเรียน Ch2 เรื่อง transport service model ก็เลยเอา framework 4 มิติ (integrity/timing/throughput/security) มาวิเคราะห์แยกแต่ละงาน แทนที่จะเดาส่งเดชว่าจะใช้ TCP หรือ UDP

**วิเคราะห์แล้วเจออะไร**
พองานโอนไฟล์ ลองไล่ทีละมิติ พบว่ามีแค่ data integrity ที่บังคับจริง (ไฟล์ผิด byte เดียวพังทั้งไฟล์) ส่วนอีกสามมิติไม่ได้บังคับไปทางไหนเลย — สรุปว่า integrity มิติเดียวก็พอจะบังคับ TCP แล้ว เพราะ TCP รับประกัน reliable in-order ให้ฟรีอยู่แล้ว ไม่ต้องเขียน retransmission logic เอง

พองาน discovery ลองไล่แบบเดียวกัน กลับพบว่า integrity ไม่บังคับ (beacon หายไปครั้งหนึ่งไม่เป็นไร ส่งซ้ำทุก 2 วิ) แต่มีมิติใหม่ที่ไม่มีในตารางเดิมคือ "โครงสร้างการสื่อสาร" — server ต้อง broadcast ไปหาทุกคนพร้อมกันโดยไม่รู้ว่ามีใครฟังอยู่บ้าง ซึ่ง TCP ทำไม่ได้เลยโดยธรรมชาติ (ต้อง connect ไปยัง IP ที่รู้แน่นอนเสมอ) จุดนี้เลยบังคับไปทาง UDP ชัดเจน — สรุปคือไม่ได้เลือกไม่ถูกระหว่าง TCP/UDP แต่มีสองงานที่ต้องการคนละอย่างจริงๆ

**ออกแบบ protocol เอง**
พอรู้ transport แล้ว ต้องออกแบบว่า client กับ server คุยกันด้วยข้อความยังไง เลยเอาโครงสร้าง SMTP ที่เรียนมาเป็นต้นแบบ (handshake → transfer → closure) — แต่ไม่ใช่ copy ทั้งดุ้น มีทั้งส่วนที่ยกมาตรงๆ และส่วนที่ต้องออกแบบใหม่เพราะ domain ต่างกัน

**ยกมาจาก SMTP ตรงๆ:**
- connect ปุ๊บ **server พูดก่อน** ด้วย greeting code (SMTP: `220 mail.server.com ESMTP` / เรา: `220 SFTP-Lite ready`) — ไม่ใช่ client เริ่มพูดก่อนแบบ HTTP
- ข้อความเป็น **line-based ASCII text จบด้วย `\r\n`** เหมือนกันเป๊ะ
- **Lockstep command-response**: ส่งคำสั่งหนึ่งอัน รอคำตอบก่อนค่อยส่งอันถัดไป
- **3-digit status code + phrase** แบบเดียวกัน (SMTP: `250 OK` / เรา: `200 OK`) — digit แรกบอก category คร่าวๆ เหมือนกัน (2xx=สำเร็จ, 4xx=client ผิด, 5xx=server ผิด)
- จบด้วย `QUIT` แล้ว server ตอบรับก่อนปิด connection (SMTP: `221 Bye` / เรา: `221 Closing`)

**เปลี่ยน เพราะไฟล์ ≠ อีเมล:**
- **วิธีบอกจุดจบ payload ต่างกันโดยสิ้นเชิง** — SMTP ใช้ `DATA` แล้วจบด้วยบรรทัด `.` เดี่ยวๆ (text terminator) แต่ไฟล์เป็น **binary** ข้างในอาจมี byte ที่หน้าตาเหมือน `.` บรรทัดเดี่ยวพอดี ใช้ terminator แบบนั้นไม่ได้ — เลยใช้**ประกาศขนาดไฟล์ล่วงหน้า** (`STORE filename <size_bytes>`) แล้วอ่านตามจำนวนนั้นเป๊ะแทน
- คำสั่งคนละชุดตามงาน (`STORE`/`GET`/`LIST`/`DELETE` แทน `MAIL FROM`/`RCPT TO`/`DATA`)
- `100 Continue` จริงๆ ยืมมาจาก **HTTP** ไม่ใช่ SMTP (HTTP's `Expect: 100-continue`) — เอามาแก้ปัญหาเดียวกัน ถ้า TA จับผิดตรงนี้ ตอบได้เลยว่าหยิบมาจาก HTTP เพราะโจทย์เดียวกัน ไม่ใช่ SMTP ล้วนๆ

**เจอ bug ตอนพัฒนา — session desync (เจอตอนไหน)**
ตอนแรกออกแบบให้ client ส่ง `STORE filename size` แล้วยิงไฟล์ตามทันที ตอน test ด้วยมือ ลองพิมพ์ชื่อไฟล์ผิดๆ ที่มี `../` เข้าไป เจอว่าคำสั่งถัดไป (`LIST`) ที่พิมพ์ตามหลัง กลับตอบแปลกๆ ผิดจากที่ควรเป็น — ไล่ดูว่าเกิดอะไรขึ้น พบว่า server ตอบ `400` ทันทีตอนเห็นชื่อไฟล์ผิด แต่ client ส่ง payload ตามไปแล้วก่อนได้รับคำตอบ bytes พวกนั้นเลยยังลอยอยู่ใน stream แล้ว server ไปอ่านมันปนกับคำสั่งถัดไป — เรียกว่า session desync แก้โดยเพิ่มขั้นตอน `100 Continue`: server ต้องบอกก่อนว่า header โอเคแล้ว ค่อยให้ client ส่งไฟล์

**เจอ bug อีกตัว — TCP ไม่มี message boundary (เจอตอนไหน)**
ตอนแรก test แค่ localhost ผ่านหมดทุกเคส แต่จำได้จากที่เรียนว่า TCP เป็น byte stream ไม่มี message boundary เลยตั้งใจไปเทสบน WiFi จริงระหว่างสองเครื่องแทนที่จะเชื่อ localhost เฉยๆ — พอลองไฟล์ใหญ่ (10MB) บน WiFi จริง เจอว่าไฟล์ที่ได้ไม่ตรงกับต้นฉบับ (`cmp` ไม่ผ่าน) เพราะโค้ดเดิมสมมติว่า `recv()` ครั้งเดียวจะได้ข้อมูลครบ ทั้งที่ WiFi จริงมันแบ่งเป็นหลาย chunk (ต่าง localhost ที่เป็น memory copy ไม่แบ่ง) — แก้เป็น loop สะสม byte ไปเรื่อยๆ จนครบตามขนาดที่ประกาศไว้

**เพิ่มความปลอดภัยพื้นฐาน (เจอตอนไหน)**
Path traversal guard (`/`, `..`) ใส่ไว้ตั้งแต่ออกแบบแรก เป็น boundary check มาตรฐาน ล่าสุดคืนก่อนส่งงาน ให้ agent ช่วย code-review รอบสุดท้าย เจอ 2 จุดที่พลาด:
- **null byte (`\x00`) ในชื่อไฟล์ ทำให้ server crash แทนที่จะตอบ `400`** — เพราะ Python ส่งชื่อไฟล์ไปเรียก OS ผ่าน C library ที่ใช้ null-terminated string ถ้ามี `\x00` แฝงอยู่กลางสตริง Python จะ `raise ValueError: embedded null byte` ทันทีเพื่อกันช่องโหว่แบบ "ตัดสตริงที่ null แล้วหลอกเช็คผ่าน" (poison null byte) — โค้ดเราเช็คแค่ `/` กับ `..` ไม่เคยเช็ค `\x00` เลย พอหลุดผ่าน guard ไปเจอ `open()`/`os.path.isfile()` ก็ raise error ที่โค้ดไม่ได้ครอบไว้ (ครอบแค่ `OSError` แต่ `ValueError` เป็นคนละ type) เลย escape ไปฆ่า connection ทั้ง thread — แก้โดยเพิ่ม `\x00` เข้า guard เดียวกับที่กัน `../`
- สอง client STORE ชื่อไฟล์เดียวกันพร้อมกัน → ไฟล์ temp ชนกัน (เขียนทับกัน) — แก้โดยตั้งชื่อไฟล์ temp ด้วย thread id ไม่ให้ชนกัน

**ทดสอบ discovery ข้ามเครื่องจริง — เรื่องยาวสุดวันนี้**
โค้ด discovery รันบนเครื่องเดียวผ่านหมด แต่พอลองข้ามเครื่องจริง (คอม↔มือถือ) บน WiFi มหาลัย กลับไม่เจอกันเลย — ลองก่อนด้วย ping (ICMP) เห็นว่ามือถือ ping มาหาคอมได้ทางเดียว แต่ส่ง UDP ไปหามือถือ (แม้แต่ unicast ตรงๆ) ไม่ถึงเลยสักครั้ง สงสัยว่าโค้ดพังหรือเปล่า เลยลองสร้างวง network เสมือนผ่าน ZeroTier เพื่อตัดปัญหาเน็ตมหาลัยออก ปรากฏว่า unicast ส่งถึงกัน แต่ broadcast ยังไม่ถึงอยู่ดี — ถึงจุดนี้เลยลองพิสูจน์ให้ชัดที่สุดว่าโค้ดถูกไหม โดยรันสอง container แยกกันจริงบนเครื่องเดียว (network namespace คนละอัน) แล้ว discovery เจอกันทันที — สรุปว่าโค้ดถูก 100% ปัญหาทั้งหมดเป็นเรื่อง network policy ของมหาลัยกับข้อจำกัดของ ZeroTier ล้วนๆ ไม่เกี่ยวกับโค้ด สุดท้ายพอกลับมาลองที่บ้านบน WiFi ธรรมดา ก็เจอกันเรื่อยๆ ทุก 2 วินาทีตามที่ออกแบบไว้จริง

**ทำไมเดาว่ามหาลัยบล็อก (เผื่อ TA ถาม "รู้ได้ไงว่าไม่ใช่โค้ด")**
WiFi องค์กร/มหาลัยที่มีอุปกรณ์แปลกหน้าเป็นพันๆ เครื่องต่อวงเดียวกัน (เช่น eduroam-style) มักเปิด **AP/client isolation** เป็นมาตรฐานความปลอดภัย — กันไม่ให้เครื่องในวงเดียวกันคุยกันเองโดยตรง (กัน ARP spoofing, worm กระจายตัว, คนสแกนหาเครื่องอื่นในวง) ที่สังเกตได้ชัดคือ **ICMP (ping) ผ่านได้ แต่ UDP ที่ device ไม่ได้เป็นฝ่าย initiate เองไม่ผ่าน** — ตรงกับ pattern ของ stateful firewall ทั่วไปที่มักปล่อย ICMP เพื่อการวินิจฉัยเครือข่าย แต่บล็อก UDP/TCP ขาเข้าที่ client ไม่ได้ร้องขอเอง เป็น policy ระดับ network ไม่เกี่ยวกับโค้ดเราเลย

## วิธีพูด
อย่าพยายามท่องสคริปต์คำต่อคำ — อ่านมันจนเข้าใจ "ทำไม" ของแต่ละจุด แล้วพูดด้วยคำตัวเองตามลำดับ สคริปต์ไว้กันลืมลำดับ ไม่ใช่บทท่อง ถ้าเล่าเรื่องราวตั้งแต่ต้น + ตอบแก่นทั้ง 6 ข้อได้โดยไม่มองสคริปต์ = พร้อมอัดจริง
