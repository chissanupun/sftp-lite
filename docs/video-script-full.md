## 0:30–3:30 — Design Recap (เปิด `slides.html`, fullscreen)

### Sheet 01/07 — Problem

ไอเดียนี้เริ่มจากเห็นเพื่อนใช้ Mac แล้วมี AirDrop กับ shared clipboard — ลากไฟล์แล้วส่งข้ามเครื่องได้ทันทีแค่อยู่ WiFi วงเดียวกัน ไม่ต้องเสียบสาย ไม่ต้องผ่านอินเทอร์เน็ต ผมใช้ Linux ไม่มีอะไรแบบนี้ให้ใช้เลย เวลาจะย้ายรูปหรือวิดีโอจากมือถือไปโน้ตบุ๊ก ต้องพึ่งส่งผ่าน LINE หรือ Messenger ให้ตัวเอง แล้วแอปพวกนี้ก็บีบอัดคุณภาพไฟล์ให้อัตโนมัติทุกครั้ง — ลองนึกภาพว่าต้องส่งพัสดุข้ามถนนแต่บริษัทขนส่งดันบังคับให้แพ็คของให้เล็กลงก่อนทุกครั้ง ทั้งที่จริงๆ เดินไปส่งเองก็ได้ ระยะแค่คืบเดียว

**SFTP-Lite** คือคำตอบของปัญหานี้ — เอาฟีลของ AirDrop มาทำเองบน Linux ส่งไฟล์แบบ raw bytes ตรงระหว่างเครื่องในวง LAN เดียวกัน ไม่บีบอัด ไม่ต้องเน็ต ไม่ต้องเสียบสาย แค่อยู่เน็ตเวิร์กเดียวกันก็พอ

### Sheet 02/07 — Scope

โปรแกรมนี้แบ่งเป็นสองระบบที่ทำงานร่วมกัน คล้ายกับที่ AirDrop เองก็มีสองงานแยกกันข้างใต้ฝาครอบเดียว — งานหาเครื่อง กับงานส่งไฟล์จริง

ระบบหลักคือ **File Transfer** มีสี่คำสั่ง: `STORE` เก็บไฟล์ขึ้น server, `GET` ดึงไฟล์ลงมา, `LIST` ดูรายชื่อไฟล์ทั้งหมด, `DELETE` ลบไฟล์ — เหมือนฟังก์ชันพื้นฐานของ FTP ที่ทุกคนคุ้นเคย

ระบบรองคือ **Discovery Beacon** — ให้ client หา server เจอเองในวง LAN โดยไม่ต้องรู้ IP ล่วงหน้า พูดง่ายๆ คือ server ตะโกนบอกทุกคนในห้องว่า "ฉันอยู่ตรงนี้นะ" ทุก 2 วินาที แทนที่จะให้ client ต้องเดินไปถามทีละคนว่าใครคือ server

ทั้งหมดนี้ควบคุมผ่าน CLI จริง ไม่ใช่แค่สคริปต์ demo — พิมพ์ `sftplite store`, `sftplite get`, `sftplite list`, `sftplite delete`, `sftplite discover` ได้เลย

### Sheet 03/07 — Transport: Main system

ทีนี้มาถึงจุดที่สำคัญที่สุดของงานนี้ — ทำไมผมเลือก transport แต่ละแบบ ไม่ใช่เดาส่งเดช แต่ไล่ตาม 4 มิติที่เรียนในวิชานี้ทีละข้อ: data integrity, timing, throughput, security

สำหรับ**การโอนไฟล์** ลองนึกภาพว่าไฟล์คือเอกสารสัญญา — ถ้าหน้าใดหน้าหนึ่งหายหรือเรียงผิดลำดับ สัญญาทั้งฉบับใช้การไม่ได้เลย นี่คือเหตุผลที่ **data integrity** เป็นมิติเดียวที่บังคับทิศทางจริงๆ ไฟล์ต้องไม่หาย ไม่เพี้ยนแม้แต่ byte เดียว ส่วน timing ไม่ time-sensitive เหมือนวิดีโอคอลที่ดีเลย์ครึ่งวินาทีแล้วรู้สึกได้ทันที, throughput เป็นแบบ elastic ทำงานได้ทั้งเน็ตช้าเร็ว ไม่มีขั้นต่ำ, ส่วน security ผมตัดสินใจไว้ตั้งใจว่าไม่ทำ encryption ระดับ protocol — เหมือน HTTP ธรรมดาที่ไม่มี TLS เป็นการจำกัดขอบเขตที่แจ้งไว้ชัดเจน ไม่ใช่ลืมทำ

เพราะฉะนั้น มีแค่ integrity มิติเดียวที่บังคับ และมันบังคับไปทาง **TCP** เพราะ TCP รับประกัน reliable, in-order delivery ให้ฟรีอยู่แล้ว — เปรียบเหมือนส่งจดหมายลงทะเบียนที่มีคนเซ็นรับ ไม่ใช่แค่โยนซองจดหมายลงกล่องแล้วหวังว่าจะถึง

### Sheet 04/07 — Transport: Secondary system

ส่วน **discovery beacon** ต้องวิเคราะห์แยกกันเลย เพราะลักษณะงานต่างกันโดยสิ้นเชิงกับการโอนไฟล์

data integrity ของ beacon ไม่บังคับเลย เพราะถ้า beacon ครั้งหนึ่งหายไปไม่เป็นไร — เหมือนประกาศทางวิทยุที่พูดซ้ำทุก 2 วินาที พลาดรอบนี้ก็รอรอบหน้าได้ ไม่ต้องเดินไปถามซ้ำ

แต่มิติที่บังคับคือ**โครงสร้างการสื่อสาร** — server ต้องประกาศตัวไปยังทุกเครื่องในวง LAN พร้อมกัน โดยไม่รู้ล่วงหน้าว่ามี client กี่เครื่องอยู่ที่ไหน นี่คือ one-to-many broadcast ซึ่ง**TCP ทำไม่ได้โดยธรรมชาติของ protocol เอง** ลองนึกภาพ TCP เป็นการโทรศัพท์ — ต้องกดเบอร์ปลายทางที่รู้แน่ๆ ก่อนถึงจะคุยกันได้ ไม่มีทางโทรออกไปหา "ทุกคนที่ได้ยิน" พร้อมกันทีเดียวได้เลย ต่างจาก UDP broadcast ที่เหมือนพูดผ่านลำโพงสาธารณะ ใครอยู่ในระยะได้ยินก็ได้ยินหมด

เพราะฉะนั้นงานนี้บังคับไปทาง **UDP**

สรุปคือ SFTP-Lite ไม่ได้เลือกไม่ถูกระหว่าง TCP กับ UDP แต่มีสองงานย่อยที่มีลักษณะต่างกันจริง แต่ละงานเลือก transport ที่เหมาะกับตัวเองแยกกัน — เหมือนบริษัทขนส่งที่ใช้รถบรรทุกปิดสำหรับส่งของมีค่า แต่ใช้รถกระจายใบปลิวสำหรับประกาศโปรโมชั่น จะใช้รถแบบเดียวกันทั้งสองงานมันก็ทำได้ แต่ไม่มีเหตุผลจะทำแบบนั้น

### Sheet 05/07 — Protocol session

นี่คือหน้าตา session ทั้งหมดของ SFTP-Lite ออกแบบให้มีโครงสร้างแบบเดียวกับ SMTP ที่เรียนในคลาส คือ handshake ก่อน แล้วค่อย transfer แล้วจบด้วย closure — เหมือนการโทรศัพท์ธุรกิจทั่วไป: ยกหูขึ้นมาต้องมีคนทักทายก่อน ("สวัสดีครับ บริษัท ABC") ค่อยเข้าเรื่อง แล้วจบด้วยการกล่าวลาก่อนวางสาย ไม่ใช่พูดเรื่องแล้ววางสายเฉยๆ

พอ client เชื่อมต่อ TCP มา server จะตอบ `220 SFTP-Lite ready` ทันที เหมือนพนักงานรับสายทักก่อนว่า "พร้อมให้บริการครับ"

ถ้า client ส่ง `STORE` พร้อมชื่อไฟล์กับขนาดไฟล์ server จะตอบ `100 Continue` ถ้า header ถูกต้อง หรือ `400 Bad Request` ถ้าผิด แล้ว client ค่อยส่ง raw bytes ตามมา จบด้วย `201 Stored` หรือถ้าเขียนไฟล์ไม่สำเร็จก็ `500 Server Error`

`GET` กับ `DELETE` ก็มี logic คล้ายกัน ตอบ `200 OK` พร้อมข้อมูล หรือ `404 Not Found` ถ้าไม่มีไฟล์ — status code พวกนี้จงใจตั้งให้คุ้นตา ใกล้เคียงกับ HTTP ที่ทุกคนเจอบ่อยอยู่แล้ว

จบ session ด้วย `QUIT` แล้ว server ตอบ `221 Closing` ก่อนปิด connection — เหมือนกล่าวลาก่อนวางสายจริงๆ

### Sheet 06/07 — Why 100 Continue

ตรงนี้คือจุดที่ผมคิดว่าน่าสนใจที่สุดของ protocol design เพราะเป็น bug จริงที่เจอตอนพัฒนา ไม่ใช่ทฤษฎีลอยๆ

ลองนึกภาพร้านอาหาร: ถ้าลูกค้าสั่งอาหารแล้วส่งวัตถุดิบเข้าครัวทันทีโดยไม่รอให้พนักงานยืนยันออเดอร์ก่อน — ถ้าพนักงานเพิ่งมาบอกทีหลังว่า "เมนูนี้หมดแล้วครับ" วัตถุดิบที่ส่งเข้าไปแล้วจะค้างอยู่ในครัว ปนกับออเดอร์ถัดไป ทำให้ครัวสับสนทั้งหมด

นี่คือสิ่งที่เกิดขึ้นจริงถ้าออกแบบแบบไร้เดียงสา: client ส่ง header แล้วยิง payload ตามทันทีโดยไม่รอคำตอบ ถ้า server เจอว่า header ผิด เช่นชื่อไฟล์มี `../` แล้วตอบ `400` ทันที แต่ client ส่ง payload ไปแล้วก่อนได้รับคำตอบ — bytes พวกนั้นจะยังค้างอยู่ใน TCP stream และถูกตีความผิดเป็นคำสั่งถัดไป ทำให้ session พังทั้งหมด เรียกว่า session desync

วิธีแก้คือบังคับให้ client รอ `100 Continue` จาก server ก่อนเสมอ ถึงจะส่ง payload ได้ — เหมือนพนักงานร้านต้องยืนยันออเดอร์ก่อนถึงจะให้ส่งวัตถุดิบเข้าครัว นี่คือ protocol-level fix ที่แก้ปัญหาตั้งแต่ระดับการออกแบบ ไม่ต้องมาแก้ implementation ทีหลัง

### Sheet 07/07 — Demo plan

ต่อไปจะโชว์ demo สดห้าอย่าง: happy path เต็มรูปแบบ, โชว์ `404`, โชว์ `400` ผ่าน raw TCP, โชว์ partial-transfer discard, และโชว์ discovery beacon — เดี๋ยวไปดูของจริงกัน

## 3:30–8:30 — Code Walkthrough (สลับไป editor)

เปิด `protocol.py` ก่อน — ชี้ที่ class `ConnBuffer`

ตรงนี้สำคัญมาก และเป็นจุดที่คนทำโปรเจกต์แบบนี้พลาดกันบ่อย: **TCP เป็น byte stream ไม่มี message boundary** ลองนึกภาพสายยางน้ำที่ต่อกันยาวๆ — น้ำที่ไหลออกมาไม่มีขีดแบ่งว่าตรงไหนคือ "แก้วที่หนึ่ง" ตรงไหนคือ "แก้วที่สอง" ผู้รับต้องเป็นคนตวงเองว่าครบปริมาณที่ต้องการหรือยัง TCP ก็เหมือนกัน ถ้าผมเรียก `recv()` ครั้งเดียวแล้วสมมติว่าจะได้ข้อมูลครบตามที่ต้องการ มันจะพังตอนใช้งานจริงบนเครือข่ายจริง เพราะ TCP อาจแบ่งส่งเป็นหลาย segment — โค้ดตรงนี้ loop สะสม bytes จนกว่าจะครบ `size_bytes` ที่ประกาศไว้ พูดประโยคนี้ตรงๆ: *"TCP has no message boundaries, so this loops until size_bytes."*

ต่อไปเปิด `server.py` ชี้ที่ `handle_store` — ตรงส่วน `100 Continue` handshake ที่เพิ่งอธิบายในสไลด์ นี่คือโค้ดจริงที่ป้องกัน session desync: ถ้า server ปฏิเสธ header ก็ตอบ `400` และ **ไม่** ส่ง `100 Continue` — client เห็นแล้วจะไม่ส่ง payload เลย ตัดปัญหาตั้งแต่ต้น

ชี้ต่อที่ partial-transfer discard — ถ้า `received != size` แปลว่า connection หลุดกลางทาง โค้ดจะลบไฟล์ `.partial` ทิ้งทันที ไม่เก็บไฟล์เสียไว้บน server — เหมือนร้านอาหารที่ถ้าลูกค้าเดินออกกลางคันตอนกำลังทำอาหาร ก็ไม่เสิร์ฟจานที่ทำค้างไว้ครึ่งๆ กลางๆ ให้ใคร

สุดท้ายชี้ path traversal guard ในฟังก์ชัน `safe_filename` — ปฏิเสธชื่อไฟล์ที่มี `/`, `..`, หรือ null byte เพื่อกันไม่ให้ client เขียนไฟล์นอก storage directory ที่กำหนด เหมือนยามที่ประตูเช็คว่าคนที่เข้ามาต้องอยู่ในโซนที่ได้รับอนุญาตเท่านั้น ไม่ปล่อยให้เดินทะลุไปโซนอื่น

## 8:30–13:30 — Live Demo (terminal, server + client คนละหน้าต่าง)

**Happy path:**
รัน `sftplite store <file>` — จะเห็น protocol lines ที่ส่ง/รับ print ออกมาเป็น `>>`/`<<` ทุกบรรทัด ตามด้วย `sftplite list` เห็นไฟล์ที่เพิ่ง store, `sftplite get` ดึงกลับมา, `sftplite delete` ลบทิ้ง

**404:**
รัน `sftplite get missing.txt` — จะได้ `404 Not Found` กลับมาตรงตามสเปก

**400 ผ่าน raw TCP:**
เปิด `nc 127.0.0.1 5050` พิมพ์เอง:
```
STORE ../etc/passwd 10
FOO bar
QUIT
```
จะเห็น `220 SFTP-Lite ready` ตามด้วย `400 Bad Request` สองครั้ง แล้ว `221 Closing` — นี่พิสูจน์ว่า protocol เป็น line-based text จริงๆ ไม่ใช่แค่ client โปรแกรมตัวเองที่คุยได้ พูดง่ายๆ คือคุยกับ server ด้วยมือเปล่าได้เลย ไม่ต้องพึ่งโปรแกรมที่เขียนเอง

**Partial-transfer discard:**
เริ่ม `sftplite store` ไฟล์ใหญ่ (เตรียมไว้ล่วงหน้า) แล้ว **Ctrl+C ที่ฝั่ง client** กลางทาง — สำคัญคือต้อง Ctrl+C ที่ client ไม่ใช่ kill server เพราะ cleanup code รันเฉพาะตอน client disconnect แล้ว `sftplite list` จะเห็นว่าไฟล์ไม่ถูกเก็บ ไม่มี `.partial` ค้างอยู่

**Discovery:**
รัน `sftplite discover` — โชว์ IP ของ server ที่เจอ พิสูจน์ว่า client หา server เจอเองจริงในวง LAN โดยไม่ต้องพิมพ์ IP เอง

## 13:30–14:30 — Wrap (กล้องหน้าตัวเอง)

สรุปคือ SFTP-Lite ใช้สอง transport สำหรับสองงานที่มีเหตุผลรองรับแยกกันชัดเจน — TCP สำหรับโอนไฟล์เพราะต้องการความถูกต้อง เหมือนจดหมายลงทะเบียน, UDP สำหรับ discovery เพราะต้อง broadcast และทนการสูญหายได้ เหมือนประกาศทางลำโพง และ protocol design ทั้งหมดพิสูจน์ได้จริง ทั้งผ่าน client ที่เขียนเอง และมือเปล่าผ่าน raw TCP ขอบคุณครับ
